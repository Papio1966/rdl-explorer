# RDL-037.2 — Canonical Entity Detail Runtime Convergence

Baseline: `7e47e5067711b9c07035f75367df4184598009b5`

Branch: `feature/rdl-0372-canonical-detail-runtime-convergence`

## Objective

Move the canonical release-aware entity detail route from committed JSON runtime authority to the generic PostgreSQL runtime API without changing its established rich-detail semantics.

Canonical route:

`/rdl/:sourceKey/:releaseKey/:entityType/:nativeIdentifier`

Production flow after this increment:

`Browser -> /api/rdl-runtime/detail -> RdlRuntimeReadService -> RdlRuntimeProjectionRepository -> PostgreSQL`

Development/plain-Vite browser flow remains explicit JSON because that harness does not host the serverless runtime API.

## Authority modes

RDL-037.2 reuses the browser authority model established in RDL-036.4 and RDL-037.1:

- `api` — PostgreSQL runtime API is authoritative.
- `dual` — JSON rollback/reference detail and API detail are compared exactly; only a matching API candidate is returned.
- `json` — explicit rollback/reference mode.

Production defaults to `api`; development defaults to `json` unless explicitly configured otherwise.

API failure or dual-read mismatch fails closed. There is no silent JSON substitution in API authority mode.

## One rich-detail semantic implementation

`src/rdl/entityDetail.ts` remains the canonical semantic projector. RDL-037.2 extracts its existing logic into an exported pure function, `projectRdlEntityDetail(...)`, while leaving the JSON loader intact as the rollback/reference wrapper.

The server runtime service uses the same pure projector over the proven PostgreSQL runtime projection. This avoids maintaining a second implementation of:

- release/package isolation;
- hierarchy parents and children;
- effective inherited class properties with closest/direct precedence;
- Tag/Equipment mappings;
- reverse class/property and class/document usage;
- discipline/document relationships;
- property units of measure;
- controlled/picklist values;
- information requirements;
- source standards;
- property/source-standard mappings;
- controlled-value/source-standard provenance;
- canonical release-aware links and relationship attributes.

## Runtime API

New read-only endpoint:

`GET /api/rdl-runtime/detail`

Mandatory query parameters:

- `sourceKey`
- `releaseKey`
- `entityType`
- `nativeIdentifier`

Schema:

`rdl-runtime-detail/v1`

A valid explicit release with no matching entity returns a successful detail response with `detail: null`. Unknown releases continue to fail closed through the existing runtime service error boundary. No latest/default release is substituted by the API.

## Projection and performance boundary

The browser makes one same-origin detail request. The server calls the already-proven full release PostgreSQL runtime projector once and applies the shared pure detail projector to that result.

RDL-037.2 intentionally does not introduce a second targeted-SQL implementation of derived relationship vocabulary. Such an optimization would duplicate complex projection semantics and increase parity risk. Internal PostgreSQL detail-query optimization can be added later behind this stable API contract without changing browser behavior.

## Scope boundaries

This increment does not change:

- RDL-036.4 shared browse authority;
- RDL-037.1 Global Search authority;
- JSON rollback/reference oracle files;
- PostgreSQL schema or migrations;
- CIS Builder;
- Assistant;
- specialist diagnostic views;
- legacy route convergence semantics.

## Deterministic acceptance

RDL-037.2 must prove:

1. the pure projector remains the single rich-detail semantic implementation for JSON and PostgreSQL;
2. representative CFIHOS, CCUS, Water current and Water historical details are exactly equal to the JSON rollback/reference oracle;
3. hierarchy, controlled values and discipline relationships remain present on representative entities;
4. API mode uses one same-origin detail request and does not load JSON;
5. JSON rollback mode makes no API request;
6. dual mode returns the API candidate only after exact parity;
7. mismatch and API-unavailable paths fail closed;
8. historical release identity remains explicit and isolated;
9. a missing entity in a valid release returns `null` rather than substituting another identity;
10. RDL-031/032 detail contracts, RDL-036.2 API compatibility and RDL-037.1 search convergence remain green;
11. regression and production build remain green;
12. rollback/reference oracle hashes remain unchanged;
13. no local Playwright is required. GitHub Actions Chromium remains the authoritative E2E/accessibility gate.
