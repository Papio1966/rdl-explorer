# RDL-036.1 — PostgreSQL Runtime Projection Parity

## Objective

Establish a source-neutral, release-aware PostgreSQL projection boundary that can reproduce the two proven browser runtime oracles exactly:

- `public/rdl-search-index.json`
- `public/rdl-relationship-index.json`

RDL-036.1 is a parity foundation only. It does **not** switch Global Search, shared browse, canonical detail, CIS, Assistant, or any other browser surface to PostgreSQL.

## Gate evidence

RDL-036 Gate 1–3 established that:

1. PostgreSQL already contains the same five governed source/release/package identities represented by the current browser projections.
2. Entity populations are already aligned for CFIHOS 2.0, CCUS 0.1/2.0, and Water / Desalination 0.1/2.0.
3. The normalized relationship model intentionally differs from the browser relationship projection in several places. Those differences belong in a runtime projection adapter rather than a database schema redesign.
4. A small set of browser-relevant source semantics was not persisted by the generic ingestion path, including synonyms and complete measurement-dimension metadata.
5. The inherited CFIHOS ingestion under-produced ambiguous class/document rows relative to the browser oracle.
6. Full replay of an already-loaded historical draft is not an appropriate enrichment mechanism once an audited successor exists: the release-identity gate correctly treats predecessor/successor name differences as changes requiring the successor audit.

## Implementation

### Normalized ingestion enrichment

`generateCfihosFormatSql.ts` now persists the source semantics needed to reconstruct the established browser search and relationship projections, including:

- synonyms and existence reasons;
- complete unit/dimension/measurement-system metadata;
- source-standard projection identity where the normalized entity name is intentionally richer than the current browser oracle;
- controlled-value source-standard and sequence metadata;
- complete information-requirement projection metadata;
- source-mapping projection attributes;
- document/discipline projection attributes;
- source-standard identity on class/document rows used to reconstruct requirement relationships.

Draft releases remain `superseded` when loaded into a fresh repository.

### CFIHOS parity repair

`generate-cfihos-ingestion-sql.ts` now:

- preserves UoM definitions and the source semantics needed by the generic search projection;
- persists complete document/discipline, information-requirement, controlled-value, and source-mapping projection semantics;
- handles ambiguous `document required per class` identities using the same fail-closed Tag/Equipment resolution used by the browser projection, instead of defaulting every non-Tag row to Equipment.

### Safe existing-database enrichment

`scripts/db-backfill-rdl-0361-runtime-projection.ts` upgrades already-loaded governed packages without replaying them as new releases.

The backfill:

- requires the exact five package identities already represented by the browser oracle;
- reuses the governed ingestion generators only to obtain deterministic entity metadata and relationship upserts;
- converts entity upserts to **metadata/source-locator only** updates;
- never deletes entities or relationships;
- never calls `rdl.assert_source_release_identity`;
- snapshots every entity type/native identifier/name/definition for all five packages inside the same PostgreSQL transaction;
- fails and rolls back if any canonical entity identity changes;
- allows only metadata enrichment, relationship-attribute refresh, and deterministic addition of governed relationship edges implied by the unchanged source packages.

This distinguishes **package enrichment** from **release identity change** and keeps the RDL-030 release-safety guard intact.

### Runtime projection repository

`RdlRuntimeProjectionRepository` is a server-side, source-neutral adapter over the normalized PostgreSQL model. It:

- selects the latest validated package per requested source/release;
- projects the existing browser search-record contract without importing browser code or public JSON files;
- translates normalized controlled-list, source-mapping, measurement, and source-standard semantics into the existing browser relationship vocabulary;
- preserves exact source/release/package identity and source-sheet provenance;
- does not infer hierarchy or relationships from names or identifier patterns.

### Deterministic parity

`db-test-rdl-0361-runtime-projection-parity.ts` compares PostgreSQL-generated projections with the committed JSON oracles for all five governed releases. The test fails closed on:

- missing or unexpected identities;
- package-key drift;
- metadata differences;
- relationship vocabulary/attribute differences;
- source-sheet provenance differences.

## Non-goals

RDL-036.1 explicitly does not:

- expose a new `/api/rdl/*` endpoint;
- alter `RdlReleaseAwareBrowse`, Global Search, or canonical detail loading;
- modify the RDL-006 CFIHOS snapshot/postgresql/dual selector;
- remove either committed browser runtime index;
- change the PostgreSQL schema;
- weaken or bypass the RDL-030 source/release identity guard;
- migrate CIS or Assistant repositories;
- run local Playwright.

## Acceptance

RDL-036.1 is complete only when:

1. the exact five governed package identities are present;
2. the non-destructive enrichment completes with canonical entity identity unchanged;
3. the PostgreSQL runtime search projection equals `rdl-search-index.json` semantically;
4. the PostgreSQL runtime relationship projection equals `rdl-relationship-index.json` semantically;
5. both committed oracle SHA-256 hashes remain unchanged;
6. RDL-030, RDL-035, regression, build and `git diff --check` remain green;
7. the exact RDL-036.1 changed-file set is present and no browser/runtime cutover file is modified.

## Next increment

Only after this parity gate is green should RDL-036.2 introduce the generic `/api/rdl/*` read boundary backed by `PgJsonClient`. Browser dual-read/cutover remains later work.

## Validation reader hardening (v4)

The RDL-036.1 projection parity test originally serialized the entire CFIHOS relationship graph through the compatibility `PsqlJsonClient` in one query. That exceeded its intentional 16 MiB stdout buffer and caused Node to emit a very large partial result on failure. The runtime projection repository now reads relationship rows in deterministic pages of 1,000 records. This changes neither PostgreSQL data nor projection semantics; it only bounds each compatibility-client response. The parity test also reduces database-read failures to a one-line diagnostic so terminal output remains bounded.

## CFIHOS multi-row requirement relationship preservation (v5)

The v4 parity run proved that PostgreSQL already contains the authoritative CFIHOS `information_requirement_class` relationship identities, but the runtime adapter could still omit some of them. The cause was projection logic: it reconstructed requirement links from the one-row-per-entity `normalized_metadata` record and ignored direct normalized JIP33 relationship rows. A CFIHOS information-requirement identity can participate in multiple JIP33 relationship rows, so metadata alone cannot represent every endpoint.

The runtime projection now preserves direct CFIHOS `information_requirement_class`, `information_requirement_document`, and `information_requirement_standard` rows after class-document-derived edges are projected, enriching them with stable requirement metadata. This preserves all authoritative endpoints and matches the committed static-generator ordering without adding or mutating database data. `information_requirement_discipline` remains intentionally outside the browser relationship projection.

No further PostgreSQL backfill is introduced by v5. The existing non-destructive enrichment remains idempotent and may be rerun by the validation wrapper.


### v6 parity repair

The static CFIHOS relationship generator emits explicit `property_unit` evidence from tag-class property rows before equipment-class property rows. Duplicate property/unit endpoints therefore use the later equipment-class evidence unless dimension-derived property metadata subsequently overwrites the endpoint. PostgreSQL relationship reads are intentionally ordered for stable retrieval rather than workbook replay order, so the runtime projection now explicitly restores this generator precedence before projecting explicit CFIHOS unit assignments. This is a projection-order correction only; normalized database identities and browser oracle files remain unchanged.

## RDL-036.1 legacy read compatibility repair

The browser-complete normalized graph intentionally contains CFIHOS `class_document` edges whose source `assetType` is not part of the original RDL-005 snapshot read contract (for example `Model_Part`). These edges are required by the RDL-035 browser oracle and therefore remain in PostgreSQL for the new runtime projection.

`PostgresRdlRepository.getDocumentsForClass()` remains the historical RDL-005/RDL-006 cutover boundary. RDL-036.1 therefore filters that legacy method to the same explicit `tag` / `equipment` asset domains used by `SnapshotRdlReadRepository`. `RdlRuntimeProjectionRepository` continues to consume the complete normalized relationship graph and is not filtered by this compatibility shim.

This preserves both contracts simultaneously:

- RDL-005/RDL-006 snapshot parity remains unchanged.
- RDL-036.1 PostgreSQL-to-browser projection parity remains exact across all five governed releases.

### Legacy dual-read compatibility refinement (v8)

The normalized PostgreSQL metadata is intentionally richer than the historical RDL-006 snapshot contract. The legacy `PostgresRdlRepository` therefore projects the exact snapshot-era metadata shape for its cutover operations, while `RdlRuntimeProjectionRepository` continues to consume the complete normalized metadata. This prevents browser-facing enrichment fields such as `existenceReason` and `measurementSystemName` from creating false RDL-006 dual-read mismatches without deleting those fields from PostgreSQL.


### Legacy JIP33 provenance compatibility refinement (v9)

The browser-complete normalized graph can contain `information_requirement_class` relationships from multiple governed evidence sources. The historical RDL-006 `getJip33RequirementsForTagClass()` contract, however, is defined only by rows from the CFIHOS `Jip33 info required spec` worksheet. The legacy `PostgresRdlRepository` now applies that exact source-locator provenance filter. `RdlRuntimeProjectionRepository` remains unchanged and continues to consume the complete normalized graph for browser-equivalent projection parity.


### Legacy metadata preservation repair (v10)

The RDL-036.1 enrichment must be additive for existing CFIHOS metadata. The v3 enrichment introduced richer information-requirement and source-mapping projection fields but used generic aliases for several source columns, which overwrote snapshot-era values required by the RDL-006 cutover contract.

The CFIHOS generator now preserves the original legacy fields alongside the richer projection fields:

- `requirementGroup` retains `document and data requirement group code`;
- `typicalDeliverable` retains `source standard document and data requirement typical deliverable`;
- `handoverStatus` retains `default required handover status code`;
- `propertyNameInSource` is retained alongside the richer `sourcePropertyName` alias.

The non-destructive backfill repairs these metadata values in place without changing entity identity or deleting relationships. The targeted validation now runs the backfill before RDL-005/RDL-006 so compatibility is tested against the repaired enriched state.

### Browser-oracle requirement attribute separation (v11)

Targeted v10 validation proved RDL-005 and RDL-006 compatibility simultaneously green, but exposed a remaining CFIHOS browser-projection mismatch: enriched legacy JIP33 metadata populated attributes that the committed relationship oracle deliberately omits because its generator uses narrower source-column aliases. v11 keeps the enriched legacy metadata and adds explicit `projection*` JIP33 fields that mirror `generate-rdl-relationship-index.ts` exactly. `RdlRuntimeProjectionRepository` uses only those projection fields for CFIHOS information-requirement relationship attributes. No browser/API cutover and no schema migration are introduced.
